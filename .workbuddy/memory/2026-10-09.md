## 最近足迹悬停图块顶部被削（overflow 连带裁剪，已修复）
- 用户需求：最近足迹图块 hover 放大时顶部被削去一块。
- 根因（真机复现实锤）：`.strip` 是 `overflow-x:auto`，**按 CSS 规范这会把 overflow-y 连带算成
  auto**（一轴非 visible，另一轴的 visible 自动变 auto）→ 条带成了竖直裁剪容器。
  卡片 hover 上浮 `translateY(-2px)`（components.css:604 `.mcard:hover`）后，卡片顶正好
  越过条带内容盒上沿 2px，被削掉一条。静止时卡片顶=条带顶，完全齐平、无任何余量。
- 修复：`.strip` 加 `padding-top:3px; margin-top:-3px`——padding 扩大裁剪盒留出上浮空间，
  负 margin 把版面位置原样补回（静止视觉零变化）。1920 实测：悬停后卡片顶在裁剪边界
  下方 1px（3 padding − 2 上浮），不再被裁。
- 注意：最近足迹/我的记录/愿望清单三个条带共用 `.strip`，一处修复全生效。
- 教训：**横向滚动容器（overflow-x:auto）天然会裁竖直方向**——容器内有 hover 位移/
  阴影/下拉等越界元素时，必须用 padding(留裁剪空间)+负 margin(补版面位置) 手法，或改用
  clip-path/内层滚动。同理适用于任何 overflow 裁剪盒里的 transform 位移元素。

## 导出 zip 增加 SQLite 快照（已完成并验证）
- 用户问「数据库文件不会被导出吗」→ 解释清楚后给三个选项，用户选「加上 db 快照（推荐）」。
- **核心发现（值得记）**：本库是 WAL 模式，服务运行期**近期写入全堆在 travelmap.db-wal 里**。
  实测宿主机 ./data/：travelmap.db 仅 44K 且 mtime 停在 10-08 00:30，而 travelmap.db-wal 2.4MB、
  mtime 10-09 02:18 —— **只 cp .db 会静默丢数据**。给用户做冷备份时必须连 -wal/-shm 一起拷，
  或先 checkpoint。
- 实现：`src/db.js` 新增 `exportDbSnapshot()` —— 先 `db.pragma('wal_checkpoint(TRUNCATE)')`
  把 WAL 合并回主库并截断归零，再 `fs.readFileSync(DB_PATH)` 返回 Buffer；checkpoint 是尽力而为
  （并发写时可能部分滞后），**失败仅 warn**，因为它不是恢复数据源。
  `server.js` 在 /api/export-zip 里把它作为 `travelmap.db` 追加进压缩包（try/catch 兜底）。
- 职责边界要分清：**data.json 是唯一的恢复数据源**（程序导入读它）；travelmap.db 只是给人的
  **兜底存档**（解压即可 sqlite3 直接查，或整文件拷回 /data 冷恢复）。导入路由本来就只处理
  `media/` 前缀条目，天然忽略根目录的 db 文件，无需改动。
- zip 最终结构：`data.json` + `travelmap.db` + `media/<key>`。
- 验证（全通过）：导出后宿主机 WAL 由 2,488,512 bytes → **0 bytes**（checkpoint 确实生效）；
  取出的快照以只读模式用 Python sqlite3 独立打开，`PRAGMA integrity_check = ok`，
  条数 places 6 / trips 1 / trip_places 3 / media 150 与 data.json **逐一对上**；
  抽样 media 的 EXIF 完好（Apple iPhone 17, f/1.6, ISO 640, 1600×1200, ready）；

## 多架构镜像推送：被国内 Docker Hub 污染卡住（进行中）
- 根因：国内 DNS 污染——`auth.docker.io`（取 token）解析到 Facebook IP 超时；`registry-1.docker.io`（manifest 读取）GET 返回 Bad Gateway/超时。单架构 arm64 之前能 push 是因为上传路径（PUT）还通、且 token 当时缓存可用。
- 已做：① 在 `~/.docker/daemon.json` 加 `registry-mirrors: [https://docker.1ms.run, https://docker.m.daocloud.io]`，用 `docker desktop restart` 重载（osascript 退出被权限拒，改用 CLI restart）；② 验证 docker.1ms.run 是真正的多架构代理（node:20-slim manifest list 含 amd64/arm64/arm/ppc64le/s390x），按 digest 拉到了真 amd64 node（`sha256:3d0f05…`）与 arm64（`sha256:10fc5f…`）到本地（tag `node-amd64-real` / `node-arm64-real`）；③ 修 Dockerfile：构建期 apt 改走多镜像兜底循环（ustc/tuna/163/huawei/aliyun/tencent），不再只依赖 aliyun——容器内 aliyun 解析到污染 IP 返回 502，宿主机却是 200，差异来自容器 DNS。
- 关键结论：① `docker push` 仍可用（PUT 路径通）；② 但 `docker manifest create` / `buildx imagetools create` 拼 manifest list 都要 ping `registry-1.docker.io`（Bad Gateway）→ **无法拼出多架构 manifest list**，故真·多架构镜像当下做不出来；③ buildx 单发多架构构建会拿本地 amd64 node 当两套平台的 base → arm64 镜像 base 层是 amd64（在 arm 机 exec format error），不可用。
- 退而求其次的可交付：分两次单架构构建——amd64 用本地 `node:20-slim`(=amd64) 构建并 push 为 `:latest`（满足 x86 部署机，用户当务之急）+ `:amd64`；arm64 用本地 `node-arm64-real` 构建并 push 为 `:arm64`（供 Mac 以后用）。两者各自 push 都行，只是合不成 manifest list。
- **最终交付（本轮完成）**：
  - amd64：`docker buildx build --platform linux/amd64 --load` → 本地 `:amd64`（digest `sha256:d0cd6a8f…`，linux/amd64），`docker push` 重试循环第 1 次成功 → 同时 push 为 `:amd64` 和 `:latest`（x86 部署机直接 `:latest` 即可）。
  - arm64：`node:20-slim` 改为可配（`Dockerfile` 加 `ARG NODE_BASE=node:20-slim`，两处 `FROM ${NODE_BASE}`）；`docker buildx build --platform linux/arm64 --load --build-arg NODE_BASE=node-arm64-real -t wyc6036/travelmap:arm64 .`（宿主机本就是 arm64，原生构建、无需 QEMU，~3min），`docker push` 重试循环第 2 次成功 → `:arm64`（digest `sha256:a873e55d…`，linux/arm64）。
  - 三标签均已在 Docker Hub：`wyc6036/travelmap:latest`(=amd64) / `:amd64` / `:arm64`。
- **真·多架构 manifest list 仍卡住**：重试循环（40 次）每次都在 `Head registry-1.docker.io/.../manifests/arm64|amd64` 返回 Bad Gateway → 无法拼 `amd64+arm64` 合一的 `:latest`。`docker-compose.prod.yml` 用 `${DH_USER}/travelmap:latest` 且未 pin platform，所以：
  - x86 部署机：`pull && up -d` 拉到 `:latest`=amd64，原生运行 ✓（用户当务之急已满足）。
  - Mac(arm64)：`docker pull wyc6036/travelmap:arm64` 显式拉 arm64；若直接 `:latest` 会因单架构 amd64 触发 Rosetta 或报错。
- 待 DNS 污染解除（`registry-1.docker.io` GET 恢复）后：重跑 `docker buildx build --platform linux/amd64,linux/arm64 --push`（即 `./publish.sh wyc6036`，建议升 v2）即可把 `:latest` 升级成真正的多架构 manifest list，那时 Mac 也能直接 `:latest`。
- 注意：`.env` 里 `DH_USER=wyc6036`；任何 `docker push` 前都要 `docker login`（agent 无凭证）。数据卷 `./data` + `./minio-data` 全程未触碰。
