## iOS 化可行性评估（只评估，未改代码）
- 结论：技术上可行，且架构有利（服务端权威、媒体处理全在后端、`/api/data` 与 places.json 同构），但**前端零 Swift 可复用**，本质是「包一层」或「重写客户端」；后端应整体保留作为同步/存储中心。
- 三条路线与量级：A PWA 1–3 人日；B Capacitor 8–15 人日；C 原生 SwiftUI 客户端 30–50 人日（MapLibre Native iOS v6.31 SPM，`MLNMapView` + UIViewRepresentable，部署目标 15.5）。全本地去后端再 +20–30 人日，不推荐。
- 已核实的真实卡点：①前端 0 处 touchstart/pointerdown，94 条 hover/drag/contextmenu 规则，详情页 32fr/68fr 双栏与 3 列磁贴都是桌面优先；②自托管为明文 http，iOS 需 ATS 例外（`NSAllowsLocalNetworking`）+ 本地网络权限文案；③鉴权是 httpOnly cookie（`tm_session`，sameSite lax，无 secure），原生客户端需 URLSession cookie 或补 bearer token；④**服务端无 HEIC 支持**（mime 映射与 sharp 均不含 heif），iOS 原生上传必须取 JPEG 兼容表示，否则 415/解码失败；⑤单文件 500MB 走 WKWebView file input 有内存风险，宜改原生后台上传。
- 分发现实：个人自托管应用上架 App Store 风险高（审核访问不到服务器 + 4.2 最小功能），实际走 TestFlight（90 天）/ 个人账号自签（7 天）/ 付费账号 Ad Hoc（1 年）。国区上架另受地图合规约束（OSM 直连瓦片不合规），与既有「不换腾讯/高德源」的决定冲突。
